**This file is ordered by execution sequence, not by severity.** Stages run top→bottom; within a stage, tasks are grouped by the file they touch so a session can land several in one pass. **Tasks marked `decision first` are blocked on a maintainer ruling, not on code** — they are collected in Stage 6 so they can be answered in one sitting.

**Why this order.** Stage 1 first because it is the only work that costs the user something they cannot get back, and it is cheap (14 of 17 are S, clustered in `hosted.rs` and `my/collection.rs`). ## Stage 1 — Destructive actions and data integrity

The user's collection is the asset. These either destroy copies, mangle rows, or ask for confirmation with a false statement. Most are S and most cluster in `app/src/backend/hosted.rs` and `app/src/my/collection.rs`, so they are cheap to sweep together — but `P6-110` is a design decision and should be answered before the rest are worked.

**The collection-deletion chain (`P6-039` → `P6-110` → `P6-188` → `P6-189` → `P6-190`) runs first and in order.** Design settled 2026-08-04, written up in [collection-deletion.md](collection-deletion.md), **accepted 2026-08-05** — deletion becomes a *soft* delete that relocates rather than destroys. `P6-039` is the prerequisite, not a sibling: the read-path filter soft delete introduces has to be added to one definition of "owned" rather than four.

- [ ] `P6-039` **Four definitions of "owned" live in `hosted.rs`, they agree today, and nothing enforces that they continue to** (rescoped 2026-07-30 — the entry said three). The `owned_by_card` view at `:100` (shared by `search` and `card_summary`), `all_cards`' inline `held` CTE at `:1274`, `collection_tree`'s `shopping_short` `o` CTE at `:417`, and `shopping_list`'s `o` CTE at `:1458`. Collapse onto one shared source, and add a test that asserts they agree. **Do this first: it is the prerequisite of the whole deletion chain below.** Soft delete requires every one of them to grow a `deleted_at IS NULL` filter, and adding it to four places and missing one produces owned counts that silently disagree between the catalog, `/my`, the tree and the shopping list — a bug with no error and no failing test. Collapsing first means the filter is added once. **S** (specs: [collection-api](collection-api.md))
- [ ] `P6-110` **Add soft deletion to `collections` and filter it out of every read path — deliberately inert, changing no behavior.** Step 2 of [collection-deletion.md](collection-deletion.md). Migration `0010_collection_soft_delete.sql`: `ALTER TABLE collections ADD COLUMN deleted_at timestamptz` plus a partial index `collections_user_parent_live_idx ON collections (user_id, parent_id) WHERE deleted_at IS NULL`. Expand-only, safe to apply ahead of the code. Then add `deleted_at IS NULL` to every site that reads collections, holdings or desires: the single collapsed "owned" source from `P6-039`, plus `collection_tree`, `list_collections`, `require_owned_collection`, `inbox_id`, `needs`, `suggested_destinations` and `search`'s ownership read. `require_owned_collection` must fail for a soft-deleted collection exactly as it does for a non-existent one, so a hidden collection can never be a move destination or a write target. **Nothing sets `deleted_at` in this task**, so every filter is a no-op and the risky half lands under no time pressure. The `ON DELETE CASCADE` on `parent_id`/`holdings`/`desires`/`card_tags` and the `ON DELETE SET NULL` on the two `moves` columns all stay — soft delete simply never fires them, which is what stops the ledger falsifying. **Acceptance:** the gate is green and no user-visible behavior changes; a manually soft-deleted row disappears from every screen and is refused as a move destination. **Prereq: `P6-039`.** **M** (specs: [collection-deletion](collection-deletion.md), [data-model](data-model.md), [collection-api](collection-api.md))
- [ ] `P6-188` **Rewrite `delete_collection` to relocate rather than destroy.** Step 3 of [collection-deletion.md](collection-deletion.md), and the task that actually closes the data-loss hole. Replace the single `DELETE FROM collections` (`hosted.rs:510`) with: set `deleted_at`; re-point every child's `parent_id` to the deleted collection's parent (children **survive** — delete removes exactly one node); move the holdings out as real ledger moves per the chosen `HaveDisposition` (`ToParent` default, `To`, `ReturnToPrevious` reusing the existing teardown mode, or `Discard`); and apply the chosen `WantDisposition` (`Discard` default, or `To`). **`Discard` writes nothing** — the rows stay attached to the hidden collection, vanish from every count because `P6-110` filters it out, and return intact on undo. Follow the `plan_move`/`plan_drop` precedent: a pure planner tested apart from the write. **The regression test that matters most:** a card held *only* in the deleted collection is still `owned` afterwards at its destination, and is *not* owned when discarded — one assertion covering all four former "owned" definitions. **Prereq: `P6-110`.** **M** (specs: [collection-deletion](collection-deletion.md), [collection-api](collection-api.md))
- [ ] `P6-189` **Give the delete confirm the two destination pickers and honest counts** (absorbs `P6-111`). Step 4 of [collection-deletion.md](collection-deletion.md). The dialog gains a picker for the haves (defaulting to the parent) and a separate one for the wants (defaulting to **"Remove from Collection"** — the agreed label for the `Discard` variant on *both* sides, resolved 2026-08-05), because a have is a physical object that must be somewhere and a want is an intention that was probably scoped to the deck being deleted. Three corrections to the copy, all of which are `P6-111`: the card count becomes **`present` for this collection only**, not `present + present_rollup` — since children now survive, rolling their cards in would overstate what is being relocated; the **wants count is stated**, where today it is never mentioned at all; and the child-collections line ("2 collections move up to Shoebox") must render from the same snapshot the write acts on, so a stale or failed tree read cannot silently omit it the way `tree_manage.rs:742`'s `descendants > 0` guard does today. **"This cannot be undone" must go** — it stops being true. Keep the property verified in `phase-6-probes/P6-017d-confirm-copy.md`: the dialog reads its own `DeleteReq` snapshot and names the collection it will actually delete. **Prereq: `P6-188`.** **M** (specs: [collection-deletion](collection-deletion.md), [app-ui](app-ui.md))
- [ ] `P6-190` **Build the two ways back — they are deliberately different operations.** Step 5 of [collection-deletion.md](collection-deletion.md). **Undo**, on the delete toast, reverses the operation whole: clear `deleted_at`, reverse every `move_id` in the receipt via the existing `undo_moves`, re-parent every id in `reparented` back. That is the misclick, which is what a toast is for. **Restore**, from a small "Recently deleted" list under My cards (name, kind, when, Restore — no purge, no permanent delete, no counts), is weaker on purpose: clear `deleted_at`, re-attach to the original parent if it is still live or top-level if not, and **leave cards and children where they now are**. Restore is not a time machine — days later the re-parented children may have been moved, renamed or deleted themselves and the relocated cards moved on, so reversing into that state is destructive rather than helpful. The copy must not promise otherwise. **Prereq: `P6-188`.** **M** (specs: [collection-deletion](collection-deletion.md), [app-ui](app-ui.md))

<summary>Original <code>P6-110</code> problem statement, kept for the record</summary>

**Deleting a collection destroys every card in it and in every collection nested under it, permanently, with no recovery path of any kind** — and the ledger does not merely fail to record it, it records something false. Verified 2026-07-29 (`specs/phase-6-probes/P6-017a-cascade.md`). `DELETE FROM collections WHERE id = $1 AND NOT is_inbox` (`app/src/backend/hosted.rs:510`) is the **entire** delete path; every other effect is the database's referential action. `collections.parent_id` cascades to descendants, and each descendant's `holdings` / `desires` / `card_tags` / deck-scoped `tags` cascade away with it. There is no soft delete, no `deleted_at`, no trash, no archive, no audit table, no undo entry, and nothing re-parents the rows — not to the parent, not to the Inbox. A card held **only** inside the deleted subtree disappears from the user's ownership entirely (`owned_by_card` is a pure aggregate over `holdings`). **The `moves` ledger survives falsified**: its two collection columns are `ON DELETE SET NULL`, and NULL in that schema does not mean "unknown", it means "external intake" (`from`) and "removal" (`to`) — so historical moves in and out of the deleted subtree silently rewrite themselves into intakes and removals, and undoing one will not put the copies back (`undo_one` skips a NULL end, `hosted.rs:2005-2010`). No move row records the deletion itself. **Decide the policy before writing code**: soft-delete + a trash view, re-parent the contents to the parent or Inbox, an explicit "and destroy N cards" confirm, or accept it and fix only the confirm (`P6-111`). Whatever is chosen must also decide what the ledger should say about a deleted collection. **Resolved 2026-08-04** — see [collection-deletion.md](collection-deletion.md).

## Stage 2 — Ship gates

Small, and each one closes a hole that lets a bad change reach `main` or prod unnoticed. `P6-124` is a hard prerequisite of `P6-108`.

- [ ] `P6-059` **`scripts/migrate.sh` can report `migrations: up to date` on a run that embedded and applied nothing — the one manual step gating a prod schema deploy.** Verified 2026-07-28 (`specs/phase-6-probes/P6-059.md`, CONFIRMED, with a root cause the original report lacked). It is not a flaky race: **cargo has no dependency edge on `migrations/` at all.** sqlx 0.8.6 emits `include_str!` per *existing* file only, its directory tracking (`proc_macro::tracked_path`) is behind `sqlx_macros_unstable`/`procmacro2_semver_exempt` (neither set here), and `app/` has no build script — so adding a `.sql` file cannot invalidate the `app` fingerprint, and the `touch app/src/db.rs` at `scripts/migrate.sh:73-80` is an mtime bet, not a guarantee. Independently, `server/src/main.rs:21-31` prints the success string on any `Ok(())` and `MIGRATOR.run` discards what it applied, so nothing can tell a real run from a no-op. There is no DB-side verification anywhere. Stake is larger than filed: `specs/app-ui.md:1391-1402` records that migration 0009 is **not** expand-first for new code, so an unmigrated prod 502s on every write while reads stay green — a partial outage that looks healthy.
  **Both fixes are required — they close different holes:**
  1. **Deterministic embed.** Add `app/build.rs` with `println!("cargo:rerun-if-changed=../migrations");` (relative to `CARGO_MANIFEST_DIR`, which is what `sqlx::migrate!("../migrations")` resolves against), then delete the `touch` from `scripts/migrate.sh:73-78`. **It must be unconditional and side-effect-free:** build scripts compile for and run on the *host* for every target, so this one runs during the hosted, native (incl. the Android NDK cross-build) and `wasm32` hydrate builds alike — nothing in it may touch sqlx, the DB or `DATABASE_URL`, which CI deliberately does not have. Costs one host-compiled unit per target build and a one-time CI rust-cache fingerprint churn. Confirm at implementation time whether cargo's directory scan also catches *edits* to existing files; the append-only new-file case is the one that is broken today and is caught.
  2. **Verify against the database, not the binary.** Read the applied set back — `Migrate::list_applied_migrations` (a trait method on a `PgConnection`, not on the pool, so this needs a connection and the trait import) compared against `MIGRATOR.iter()`. `app/src/db.rs:41-56` returns the applied/embedded versions instead of `()`; `server/src/main.rs:21-31` prints those versions instead of the fixed string. **This is the fix that removes the failure mode** — (1) alone makes the embed race unlikely but leaves a silent success for every *other* no-op cause (wrong branch URL, stale cross-target binary, aborted `cargo run`).
  **Acceptance:** a migrate run distinguishes "applied 0010" from "0010 already present" from "0010 not embedded", and cannot print success having applied nothing. Also correct the now-false "guarantee[s] a re-embed" sentence at `specs/data-model.md:555-559`. `--quiet` at `scripts/migrate.sh:80` is cargo's, not the binary's, so the version log prints through it — dropping it is optional once (2) lands. **S** (specs: [delivery-pipeline](delivery-pipeline.md), [data-model](data-model.md))
