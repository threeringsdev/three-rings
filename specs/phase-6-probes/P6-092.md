# P6-092 — The merge gate never builds (or launches) a Tauri release, so nothing in CI exercises the embedded-server startup path that shipped a crash-on-launch to `latest`
Probed 2026-07-28 against 2cd1b6d.

## Verdict: CONFIRMED (one sub-claim WRONG: "no GUI is needed"; the triage row's P6-089 fold-in is imprecise)

The gap is real and, if anything, **larger** than the entry states. The 2026-07-20
*bug* is fixed (b3743e1); the *process gap* the entry is about is untouched.

## Evidence

### (a) "The merge gate never builds a Tauri **release**" → CONFIRMED
`.github/workflows/validate.yml` — the complete list of build-ish steps is:
`cargo fmt`, five `cargo clippy` lines, `cargo test --workspace --exclude frontend`,
and `cargo leptos build --release`. None of them produces a release `three_rings`.

- The clippy and test lines run in the **dev** profile (cargo's default; no
  `--release` anywhere in the file, and no `debug-assertions` override in
  `Cargo.toml`'s profiles or `.cargo/config.toml`, which only sets `LEPTOS_OUTPUT_NAME`).
- `cargo leptos build --release` builds `bin-package = "server"` and
  `lib-package = "frontend"` (`Cargo.toml` `[[workspace.metadata.leptos]]`) —
  `three_rings` is not in that graph.
- `grep -rn "three_rings\|tauri build" .github/workflows/` returns exactly two
  hits, both in `artifacts.yml`: `:156` `cargo tauri android build --apk --target aarch64`
  and `:277` `cargo tauri build`. Both are in `workflow_dispatch`-only jobs, not
  the merge gate.

### (b) "The gate only *lint-checks* `src-tauri`" → CONFIRMED, and **understated**
The entire embedded-server startup path is `#[cfg(not(debug_assertions))]`:
`src-tauri/src/lib.rs:54` opens the attribute, the block runs to `:274`. Because
every gate step compiles `src-tauri` in the dev profile, **that block is never
compiled in CI at all** — not linted, not type-checked. A type error or a bad
`use` inside lines 55–273 would pass the whole gate green. Same for
`ServerPort` (`:12`, `#[cfg(all(not(debug_assertions), target_os = "android"))]`)
and the `on_page_load` body (`:293`).

Corollary that matters for the fix: a **debug** `cargo build -p three_rings`
would not compile this code either. Any step meant to cover P6-092 must be
`--release`.

### (c) "nothing ever exercises the embedded-server startup path" → CONFIRMED
- `grep -rn "#\[test\]\|#\[cfg(test)\]" src-tauri/` → zero hits. `cargo test
  --workspace` compiles `three_rings` and runs nothing from it.
- `artifacts.yml` *builds* the `.dmg` and APK but never launches them.
- The only launch assertion in the repo is `scripts/smoke-android.sh` (67 lines) —
  host-only, manual, emulator-dependent, invoked by the `android-smoke` skill at
  phase boundaries (`specs/ui-work-loop.md:379-382`). Nothing in CI calls it.

### (d) "the validate suite's own web coverage cannot see it because `server` is `#[tokio::main]`" → CONFIRMED
`server/src/main.rs:4` is `#[tokio::main]`; `:91` is `let app = app::build_router(leptos_options);`,
inside that runtime. The identical call in the Tauri shell (`src-tauri/src/lib.rs:162-163`)
is the one that needed `tauri::async_runtime::block_on`.

### (e) The root-cause narrative (render → `Resource` → `tokio::spawn` → no runtime) → CONFIRMED as history; the bug itself is FIXED
`app/src/lib.rs:1608` `pub fn build_router(...)`, `:1613` `let routes = generate_route_list(App);`.
Fix landed in b3743e1 "fix(tauri): run build_router inside the Tokio runtime context (#46)",
now `src-tauri/src/lib.rs:162-163`:
```rust
let router =
    tauri::async_runtime::block_on(async move { app::build_router(conf.leptos_options) });
```
`specs/architecture-spike.md:145-173` records the finding. That commit's own message
ends with "Also files the process gap that let this ship: the merge gate never
builds a Tauri release, only lint-checks it" — i.e. P6-092 *is* the filed gap, and
nothing has closed it since.

### (f) "the crash was pre-window, so no GUI is needed" → **WRONG**
Tauri 2.11.2 (`Cargo.lock`), `~/.cargo/registry/.../tauri-2.11.2/src/app.rs`:
```
2516:  for window_config in app.config().app.windows.iter().filter(|w| w.create) {
2517:    WebviewWindowBuilder::from_config(app.handle(), window_config)?.build()?;
...
2523:    (setup)(app).map_err(|e| crate::Error::Setup(e.into()))?;
```
Config windows are created **before** the setup hook, and `Builder::build`
(`:2235`) constructs the runtime/event loop (GTK on Linux) before either. Our own
code confirms it: `src-tauri/src/lib.rs:257` calls `app.get_webview_window("main")`
inside setup and expects it to exist. `tauri.conf.json` declares one window.

The crash was pre-*navigation*, not pre-*window*. A headless Linux launch
assertion therefore needs a virtual display — `xvfb-run` / `Xvfb` + `DISPLAY`.
That is one apt package, so the "cheapest real coverage" conclusion survives, but
the stated reason for it does not, and the step is missing from the entry's plan.

### (g) "a linux release build in the existing gate job would have caught this one" → PARTLY
The panic (`tokio::spawn` with no runtime in scope) is genuinely
platform-independent, so a linux release **launch** would have caught it. A linux
release **build** would not — it is a runtime panic, not a compile error. The
entry gets this right in its own next clause ("headless launch assertion, not a
full bundle"); the *triage row* does not: "one `cargo build -p three_rings` step
covers both [P6-089 and P6-092]" is false for P6-092 at any profile. Precisely:

| step | covers P6-089 (recursion limit, codegen query) | covers P6-092 (startup panic) |
|---|---|---|
| `cargo build -p three_rings` (debug) | yes — P6-089's own measurement | no — block is cfg'd out and it's a runtime panic |
| `cargo build --release -p three_rings` | yes | no — compiles the block, never runs it |
| release build **+ headless launch + HTTP assert** | yes | yes |

So they share a *prerequisite*, not a fix. Merging them is fine only if the merged
task is scoped to the launch assertion (which subsumes the build).

### (h) "assert it binds its port and answers `GET /catalog`" → workable, with two unnamed prerequisites
1. **Resources must be staged.** For a raw `target/release/three_rings`,
   `resource_dir()` takes the cargo-output-directory branch
   (`tauri-utils-2.9.2/src/platform.rs:284-302`) and returns the exe dir. The
   setup then reads `resource_dir/site` and `resource_dir/Cargo.toml`
   (`src-tauri/src/lib.rs:119-133`), neither of which a plain `cargo build`
   produces. Two `cp`s, but they must be in the step. (`tauri.conf.json`'s
   `bundle.resources` only applies to real bundles.)
2. **`/catalog` under the `native` backend goes over the network.**
   `app/src/backend/native.rs:29` `DEFAULT_WEB_ORIGIN = "https://three-rings-6p5o.onrender.com"`
   (override `TR_WEB_ORIGIN`, `:551`). The assertion should be "binds + HTTP 200 +
   SSR shell present", not "catalog rows present" — otherwise the gate goes red
   when Render is asleep. `/catalog` is a Leptos page route (mounted via
   `leptos_routes` in `build_router`), not an explicit axum route, so 200 + shell
   is the right signal.

**`implemented`** — the task is unblocked by the queue rules.

## If it is real, what fixing it touches
- `.github/workflows/validate.yml` — one new step (plus `xvfb` in the existing
  apt line, which already installs Tauri's GTK/webkit deps).
- Staging: `cp Cargo.toml target/release/` and the `cargo leptos build --release`
  site output into `target/release/site/`. Note the gate exports
  `CARGO_TARGET_DIR=target/gate` **locally only** — CI omits it, so CI's site
  output is at `target/site` (`CLAUDE.md`, `Cargo.toml` `site-root` marker). A
  local reproduction of the new step has to account for that difference.
- Nothing in `src-tauri/` needs to change for the assertion itself. But note the
  step will be the first thing in CI that ever compiles
  `src-tauri/src/lib.rs:55-273`, so it may surface latent errors in code that has
  never been checked by anything but a human's local `cargo tauri build`.
- Bigger than it looks, in order of surprise: (1) needs a virtual display, contra
  the entry; (2) needs resource staging or `get_configuration` fails before the
  interesting code runs; (3) the process must be killed after the assert — the
  binary runs an event loop and will not exit on its own; (4) release compile of
  `three_rings` on the gate runner adds real minutes to a gate that runs on every
  PR push, which is the trade-off the "Decide where it runs" clause is pointing at
  (gate vs. a separate cheap workflow vs. folding into `artifacts.yml`).

## Open — needs a runtime check
Two, both blocked by the read-only/no-build constraint:

1. **Does `xvfb-run ./target/release/three_rings` actually reach the setup hook on
   linux, and does the port bind?** Exact check, on a linux box with Tauri's deps:
   ```
   cargo leptos build --release
   cargo build --release -p three_rings
   cp Cargo.toml target/release/ && cp -r target/site target/release/site
   xvfb-run -a ./target/release/three_rings &
   # then: assert a listener appeared on 127.0.0.1 (ss -ltn) and curl -sf that port/catalog
   ```
   This settles both (f) — whether a display is genuinely required — and (h1) —
   whether exe-dir resource staging is sufficient.
2. **How long does the release `three_rings` compile take on the Blacksmith
   4-vCPU linux runner, warm cache?** That number, not correctness, decides
   "gate vs. separate workflow". Only a CI run answers it.

Neither affects the verdict: the gate demonstrably has no release build and no
launch of any kind today.
