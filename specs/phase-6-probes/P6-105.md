## If it is real, what fixing it touches
- `app/src/ingest/scryfall.rs` — three new client methods: paged `/cards/manifest`
  (15,000/page, ~8 pages, 10 req/min), `POST /cards/collection` (75 ids/req, 2 req/s,
  handle the `not_found` array), paged `/migrations`. Rate limiting is currently
  absent from the client entirely (the bulk path only ever hits rate-limit-free
  `*.scryfall.io` plus two one-shot API calls), so a pacing/backoff layer is new
  surface — and a 429 costs a 30 s lockout, repeat offenders get banned.
- `app/src/ingest/mod.rs` — `Mode::Update` + the diff (unknown ids → hydrate; advanced
  `data_updated_at`/`image_updated_at` → hydrate; absent-from-manifest → log, never
  delete) and the **baseline mode**: the first sweep after a bulk run must record
  manifest timestamps *without* hydrating rows that already exist
  (`specs/catalog-ingestion.md:206-212`) — otherwise day one hydrates all ~116K rows.
- `app/src/ingest/upsert.rs` — writers for the two `manifest_*_updated_at` columns
  (currently never written) and the migrations merge/delete reconciliation with the
  "iff unreferenced" guard against `holdings`/`desires`/`moves`.
- `server/src/main.rs:40-49` — accept `update` in the `--ingest` match and its usage
  string.
- Render dashboard (outside the repo) — a new cron service on the same root
  `Dockerfile`, command `server --ingest update`, holding the `catalog_ingest`
  credential; plus the standing rule that the web service keeps only `app_runtime`.
- `specs/catalog-ingestion.md` — five open questions to close at execution (COPY-vs-batch
  for the full load, manifest field population, cron schedule expression / instance size /
  build-minutes) and the status flip to `implemented`.

**Bigger than it looks, three ways:**
1. `specs/catalog-ingestion.md:494-498` — the prod POC ran against **zero user rows**.
   "That will not be true next time — the full-load task should assume live user data
   and re-read the hash-gated upsert guarantees before running." A 116K-row bulk load
   against a live prod database with real `holdings`/`desires` FK'ing `printings` is a
   different risk class than the additive run that was verified.
2. `specs/TODO-Phase-6-triage.md:125` (P6-072f) — `jsonb_array_elements(p.faces)` hard-errors
   the whole detail/search/summary query on a non-array. It is unreachable via today's
   ingester *because the POC subset happens not to produce one*; a full load over all
   ~116K printings is exactly the event that could surface it. That entry explicitly says
   "note or harden **before** P6-105 changes the ingest" — treat it as a prerequisite,
   not a sibling.
3. Scale-out effects the entry doesn't mention: catalog size goes 2.6% → 100%, which is
   the trigger condition for the parked full-catalog disambiguation task
   (`specs/TODO.md:106`) and the large-collection profiling task (`specs/TODO.md:108`).
   Those become *newly testable*, and possibly newly broken.
