# P6-068 — `/my/collections/:id` detaches and re-attaches its whole DOM subtree after every `?q=` navigation
Probed 2026-07-28 against 91634da.

## Verdict: CONFIRMED

The behaviour is real, still present at HEAD, and the mechanism is now identified
in code (no runtime instrumentation needed to name it). Only the *timing* number
in the entry ("~800 ms after") is not derivable statically.

## Evidence

- **"detaches and re-attaches its whole DOM subtree"** → CONFIRMED.
  `app/src/shell.rs:118-154` — `RequireAuth` wraps the entire `/my/*` page tree in
  a **`<Suspense>`** (not a `Transition`), rendering `<Outlet/>` inside its
  `Suspend`. When that boundary re-suspends, `leptos-0.8.14/src/suspense_component.rs:184`
  computes `show_b = !none_pending.get() && (!TRANSITION || nth_run < 2)`; with
  `TRANSITION = false` that is `true` on *every* re-suspension, and
  `tachys-0.2.18/src/view/either.rs:493-511` (`EitherKeepAlive::rebuild`) then does
  `a.insert_before_this(b); a.unmount()` — the children's state is **kept alive**
  and the *same DOM nodes* are removed, then re-inserted when the boundary settles.
  That is exactly the entry's "gone … same nodes back": a rebuild would produce new
  nodes; keep-alive re-inserts the identical ones.

- **"~800 ms after every `?q=` navigation … gone ~400 ms"** → PARTLY / not
  statically checkable. The ~400 ms out-of-document window is exactly what the
  mechanism predicts (it is the `collection_view` round-trip: the boundary is
  pending from the moment `view_res` re-runs until its future resolves,
  `reactive_graph-0.2.14/src/computed/async_derived/arc_async_derived.rs:372-386`).
  The **~800 ms offset before the detach starts is not derivable from the code** —
  the mechanism says the unmount should begin within a tick of the navigation. See
  "Open" below.

- **"`/catalog` and `/my` do not"** → CONFIRMED, and for two different reasons.
  `/catalog` (`app/src/lib.rs:117`) is a direct child of `AppShell`, which has **no
  `Suspense` above `<Outlet/>`** (`app/src/shell.rs:259-267`) — so
  `use_context::<SuspenseContext>()` returns `None` there and nothing can register.
  `/my` (`app/src/my/all_cards.rs:148-277`) *is* under `RequireAuth`, but its
  resource `rows` is only ever touched inside its own `<Transition>` (`.await` at
  line 230) or via `refetch()` (line 256) — never read outside a boundary. Same for
  `/my/all`, `/my/shopping` (`app/src/my/shopping.rs:76-132`) and
  `/my/collections/:id/needs` (`app/src/my/needs.rs:318-379`; `needs_res` is only
  awaited inside its `Transition` and refetched).

- **"silently closes any native popover … removing a showing popover fires no
  `toggle`, so the Rust `open` signal desyncs"** → CONFIRMED.
  `app/src/components/ui/popover.rs:200-242`: the Rust `open` signal is re-synced
  **only** from the native `on:toggle` handler. Overlays that live inside the
  detached subtree include the header's `<ContextMenu id="collection-header">`
  (`app/src/my/collection.rs:735`) and every row's `CardPreview` hover card
  (`app/src/my/collection.rs:1383`) — `context_menu.rs`, `hover_card.rs`,
  `popover.rs`, `command.rs`, `collapsible.rs` and `sonner.rs` all use the native
  popover API.

- **"rebuilds the DOM per search"** → WRONG as literally worded, harmless in
  effect. `EitherKeepAlive` does **not** rebuild — it unmounts and re-inserts the
  identical node tree (`either.rs:493-511`). So there is no per-search re-render
  cost; the damage is entirely from the detach itself (focus, popover state,
  scroll/IntersectionObserver). The entry's own parenthetical ("same nodes back")
  already says this, so the two halves of the entry disagree with each other.

- **"blurs the focused field"** → CONFIRMED by construction (removing the focused
  element from the document moves focus to `<body>`; re-insertion does not restore
  it) and by the shipped workaround.

- **"the quick-add panel only survives it via a 120 ms focus keeper, a workaround
  at one call site"** → CONFIRMED. `app/src/components/quick_add.rs:402-439` —
  a `set_interval_with_handle` at `Duration::from_millis(120)` that refocuses
  `focus_target` when `document.activeElement` is `<body>` and the panel is open.
  `QuickAddPanel` has exactly one call site, `app/src/my/collection.rs:310`.

- **Already documented as known.** `app/src/shell.rs:173-177` and
  `specs/app-ui.md:1602-1621` both record the detach as measured fact; the spec
  says "the cause is upstream and is filed" — this entry is that filing.

## Mechanism (if found)

`/my/collections/:id` is the only route that **reads its own `Resource` outside
every local suspense boundary while sitting under `RequireAuth`'s `<Suspense>`.**

The registration path is `reactive_graph-0.2.14/.../arc_async_derived.rs:629-667`:

```rust
fn try_read_untracked(&self) -> Option<Self::Value> {
    if let Some(suspense_context) = use_context::<SuspenseContext>() {
        let handle = suspense_context.task_id();
        ...
        // register the suspense context with our list of them,
        // to be notified later if this re-runs
        self.inner.write().or_poisoned().suspenses.push(suspense_context);
    }
    ...
}
```

Every `Resource::get()` / `.read()` looks up the **nearest `SuspenseContext` in
the owner chain — whatever it is** — and stores it on the resource. When the
resource later re-runs, `arc_async_derived.rs:372-376` mints a fresh pending
`TaskHandle` for each stored context:

```rust
let suspense_ids = mem::take(&mut guard.suspenses)
    .into_iter().map(|sc| sc.task_id()).collect::<Vec<_>>();
guard.pending_suspenses.extend(suspense_ids);
```

…and drops them only after `fut.await` (line 384). So the boundary is pending for
the whole fetch.

On this page there are two such reads, both in `CollectionPage`'s own scope,
outside both of its `<Transition>`s:

- `app/src/my/collection.rs:217-221` — the `here_delta` zeroing Effect,
  `if view_res.get().is_some() { here_delta.set(0); }`. **Being in an `Effect`
  does not help**: `in_effect_scope()` only suppresses the debug *warning*
  (`leptos_server-0.8.6/src/resource.rs:947`); the suspense registration at
  `arc_async_derived.rs:634` is unconditional.
- `app/src/my/collection.rs:232-236` — the `resolved` memo (`view_res.get()`),
  which feeds `quick_add_destination` / `quick_add_kind` / `quick_add_present`
  (lines 237-260) into `<QuickAddPanel>` at line 310 — rendered *between* the two
  Transitions, deliberately (line 264-267).

The nearest `SuspenseContext` for those reads is the one provided by
`RequireAuth`'s `<Suspense>` (`app/src/shell.rs:122`;
`suspense_component.rs:119`), because `AppShell` provides none and the route's own
`Transition` contexts (`transition.rs:104`) are below, not above, these reads.

So the chain is:

`?q=` navigation → `url_q` memo changes (`collection.rs:154`) → `view_res` re-runs
(`collection.rs:173-199`) → the stored **`RequireAuth` `SuspenseContext`** gets a
pending task → `none_pending` flips false → `SuspenseBoundary<false>`'s
`RenderEffect` sets `show_b = true` → `EitherKeepAlive` **unmounts the entire
`<Outlet/>` subtree** (the whole `data-testid="collection-page"` div, query bar
included) and mounts `RequireAuth`'s `<p class="text-muted-foreground p-8 text-sm">"Loading…"</p>`
fallback → the fetch resolves → the *same* nodes are re-inserted.

`/catalog` has no ancestor `SuspenseContext` at all, and `/my`, `/my/all`,
`/my/shopping`, `/my/collections/:id/needs` keep every resource read inside a
local boundary. That is the difference the entry asked for.

Two secondary confirmations that this is not the *router*:
- `leptos_router-0.8.10/src/nested_router.rs:152-162` — on a query-only
  navigation the path is unchanged, so `NestedRoutesView::rebuild` only does
  `outlet.url.set(...)` and returns; it never re-triggers the outlet.
- `nested_router.rs:1098-1112` — `Outlet` re-renders only on `child.trigger`,
  which is notified only on a *path* change. So "the router removes and re-inserts
  this page's whole subtree" (`quick_add.rs:54`, `specs/app-ui.md:1606`) misnames
  the culprit: it is the auth guard's `Suspense`, not the router.

## If it is real, what fixing it touches

Two candidate fixes, and they are very different sizes.

**Option A — `RequireAuth` uses `<Transition>` instead of `<Suspense>`**
(`app/src/shell.rs:122-152`). One-token change; `SuspenseBoundary<true>` never
swaps to the fallback after `nth_run >= 2` (`suspense_component.rs:184`), so the
page stays mounted through any re-suspension. Fixes the whole `/my/*` subtree at
once. What to check before taking it: the guard's redirect arm (`<Redirect/>` /
`leptos_axum::redirect`) now renders *behind* a still-visible old page on a
session change, and the route is `SsrMode::Async` — the SSR path for
`SuspenseBoundary<true>` differs from `<false>` and this is the guard that sets a
real 302 (`app/src/lib.rs:129-156`, `shell.rs:145-147`).

**Option B — stop reading `view_res` outside a boundary**
(`app/src/my/collection.rs:217-260`). Bigger than it looks, for one specific
reason: **moving a read into an `Effect` is not a fix** — the registration at
`arc_async_derived.rs:634` ignores `in_effect_scope()`, so `/catalog`'s
`last_good` / `count_after_hydrate` idiom (`app/src/catalog.rs:227-231`,
`:305-311`) would *not* work here; it only looks safe on `/catalog` because that
route has no ancestor `SuspenseContext`. A real Option B means the existing
`Transition` bodies (`collection.rs:282-300`, `:333-369`) writing plain
`RwSignal`s that `QuickAddPanel` and the `here_delta` reset then read — which
changes when the quick-add destination/kind/present become available relative to
the header and table, and touches the `here_delta` invariant documented at
`collection.rs:206-221`.

**Latent, worth noting either way:** `/catalog`'s two Effects read `results` in
render scope and are safe *only* because nothing above `<Outlet/>` in `AppShell`
provides a `SuspenseContext`. Adding any `Suspense` above `AppShell`'s `<Outlet/>`
would give `/catalog` and `/cards/:id` the same defect for free.

Also touched by any fix: `app/src/components/quick_add.rs:402-439` (the 120 ms
focus keeper becomes dead weight), `specs/app-ui.md:1602-1621` and
`app/src/shell.rs:173-177` (both describe the cause as "the router", which is
wrong — see above).

## Follow-up (2026-07-28) — Option A vs Option B, settled on facts

**1. The two reads are in the component setup body, not the view tree.**
`collection.rs:217-260` all sit above `view! {` (line 262). `Suspense`/`Transition`
provide their `SuspenseContext` on their *own* `Owner`
(`suspense_component.rs:106-121`, `transition.rs:91-106`), and children see it only
because children are built under that owner. Setup-body statements run under
`CollectionPage`'s owner, which is an **ancestor** of every boundary in its view —
so no boundary placed in the view tree can ever be an ancestor of these reads.
Wrapping them in a nearer `<Transition>` is therefore **structurally impossible**
as long as they stay in the setup body. Moving the *consumers* inside a boundary is
possible but is ruled out by an existing documented constraint: the query bar is
deliberately outside both Transitions (`collection.rs:264-267`) because a
Transition rebuild would rebuild the `<input>` under the caret.

**2. Option B's shape, and the property it turns on.** Confirmed:
`ArcRwSignal::try_read_untracked` (`reactive_graph-0.2.14/src/signal/arc_rw.rs:251-257`)
just returns the value — **no `use_context::<SuspenseContext>()` lookup at all**,
unlike `ArcAsyncDerived`'s (`arc_async_derived.rs:629-667`). So a plain signal can
never re-suspend any boundary, and the guard becomes unreachable from a query
refresh. The minimal correct shape is: the reads move into a scope whose owner is
**under the page's own `Transition`** — either written directly from the
`Suspend` body (which already holds the resolved `CollectionView`,
`collection.rs:282-300` / `:333-369`) or from an `Effect` created there — and the
out-of-boundary consumers read plain `RwSignal`s instead of `view_res`.
**A third shape exists and I should name it:** `SuspenseContext` is public with a
public `tasks` field (`reactive_graph .../async_derived/mod.rs:114,146-149`), so
`provide_context(SuspenseContext { tasks: ArcRwSignal::new(Default::default()) })`
at the top of `CollectionPage` installs a *decoy* boundary that swallows the
registrations before they reach `RequireAuth`. It is ~2 lines, needs no new
dependency (the `SlotMap` type is inferred), and requires no re-derivation — but it
is a boundary with no view, i.e. a lie in the reactive graph, and it silently
shadows for the whole subtree. Viable; not recommended without a comment
explaining exactly this report.

**3. Option B's cost.** One file, two producing sites and four consuming sites:
the `here_delta` Effect (`collection.rs:217-221`), the `resolved` memo and its
three derivatives (`:232-260`), and the props at `:288` and `:321-323`. Roughly
40-55 lines rearranged. Two things need re-derivation, and they are the reason
this is not a pure mechanical move:
- **The `here_delta` invariant** (`collection.rs:206-221`). Today the reset keys on
  `view_res.get().is_some()` precisely because an in-flight resource reads `None`.
  A signal written from inside the Transition body fires when the new payload
  *renders*, which matches the stated intent more exactly — but the header and the
  table are **two separate boundaries awaiting the same resource**
  (`:279-301`, `:330-370`), so whichever one writes it decides the ordering
  relative to the other, and that ordering is what the invariant is about.
- **Quick-add prop timing.** `resolved` currently collapses to `None` while a
  re-search is in flight, so `⏎` mid-search hits the "Still loading this
  collection" guard (`quick_add.rs:449-455`). A signal would retain the last
  destination instead. That is arguably better, but it is a **behaviour change**,
  not a refactor, and it is on the metric path (the keystroke loop).
Size: **M** — mechanically S (one file, no new types), M once the two semantic
decisions above and their e2e coverage are counted.

**4. Option A's auth behaviour.**
(a) **The first-load fallback still renders.** `show_b = !none_pending.get() && (!TRANSITION || nth_run < 2)`
(`suspense_component.rs:184`, with the comment at `:179-183` saying exactly this):
under `TRANSITION = true` the fallback is still shown on the first two runs, so
`RequireAuth`'s `"Loading…"` behaves identically on a cold client render.
(b) **No stale-authenticated-page risk exists today, but the trade is real in
principle.** `CurrentUserResource` is `Resource::new(|| (), |_| fetch_current_user())`
— a **constant source** (`shell.rs:26-29`) — and it is **never refetched**: every
`.0.refetch()` in `app/src` targets the collection tree, none the user resource.
Sign-out is a `hard_navigate` full document load (`shell.rs:535-543`), and the
`/` redirect and guard arms (`shell.rs:101-109`, `:134-148`) only re-evaluate when
that resource changes. So the guard cannot re-run mid-session at all today, under
either component. The SSR/hydration path is also unaffected: `RenderHtml` is
implemented **once** for `SuspenseBoundary<const TRANSITION: bool, …>`
(`suspense_component.rs:249`), so `SsrMode::Async` (`lib.rs:141-145`) and the
`leptos_axum::redirect` 302 (`shell.rs:145-147`) are byte-identical either way.
The honest statement of the trade: Option A is inert *today* and becomes a
latent hazard the moment anyone makes `CurrentUserResource` refetchable, at which
point a Transition would keep signed-in content on screen through the re-check.
That is a real argument for Option B being the *correct* fix rather than the
merely-sufficient one — Option A leaves the mis-wiring in place and only removes
the surface it damages.

## Open — needs a runtime check

One check settles both the causation and the 800 ms number, and it is a single
observation in an already-running browser:

> On `/my/collections/:id` with the devtools Elements panel (or a
> `MutationObserver` on `<main>`), type into the search field and watch what
> replaces `div[data-testid="collection-page"]` during the gap.
> **The mechanism predicts `RequireAuth`'s fallback — `<p class="text-muted-foreground p-8 text-sm">Loading…</p>` (`app/src/shell.rs:123`) — appears in its place for the duration.**
> If that paragraph appears, the diagnosis above is confirmed end to end and the
> fix is Option A or B. If the subtree is replaced by *nothing*, the cause is
> elsewhere and this report is wrong.

Second, smaller open question: time the gap from the `popstate`/`navigate` call
rather than from the keystroke. The mechanism predicts the detach begins within a
tick of the navigation, not ~800 ms after it; the reported 800 ms is most likely
measured from the keystroke (250 ms debounce, `query_bar.rs:59`) plus request
latency, but that is a guess and the code cannot settle it.
