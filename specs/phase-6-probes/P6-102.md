# P6-102 — Google sign-in on web "doesn't open another browser tab" and the terminal "you can close this tab" page "doesn't redirect back to the app"; works on desktop, not on web
Probed 2026-07-28 against 2cd1b6d.

## Verdict: PARTLY — claim (a) is true but **deliberate, not a defect**; claim (b) is **WRONG as written about the web flow** (that page is native-only and is never served to a web browser). The underlying complaint the triage row states — "sign-in on the deployed platform dead-ends" — is **UNVERIFIABLE from code**: I found no web-only defect in the Google path, and none of that code has changed since it was last verified live.

## Evidence

### (a) "Auth flow on web doesn't open another browser tab" → TRUE, but by design
`app/src/auth_pages.rs:158-231` (`GoogleButton`) is the whole client half. Its own
doc comment states the split: *"Web: navigates this window into the hosted flow
(`/auth/callback` lands us back signed in). Tauri: opens the flow in the system
browser and polls `current_user`…"* (`:152-157`).

- `app/src/auth_pages.rs:180` — `if tauri_open_url(&url, on_reject) { …poll… } else { redirect_browser(&url) }`.
- `tauri_open_url` (`:70-115`) returns `false` whenever `window.__TAURI__` is
  absent (`:77-82`) — i.e. always in a plain browser.
- `redirect_browser` (`:36-47`) is `w.location().set_href(url)` — a **same-tab**
  top-level navigation.

Same-tab navigation *is* the correct web OAuth pattern (a new tab exists on
desktop only because Google refuses OAuth inside an embedded webview, so the
Tauri shell must hand off to the system browser). So the clause is factually
accurate and is not, on its own, a bug.

### (b) "final 'you can close this tab' doesn't redirect back to the app" → WRONG as a statement about web
There are exactly two "close this tab" strings in the repo, both in
`app/src/lib.rs`, and **neither is reachable in the deployed web flow**:

1. `app/src/lib.rs:1520-1523` — *"Signed in — you can close this tab and return to
   Three Rings."* Served by `/auth/callback` **only** inside
   `if native { … }` (`:1507`), where `native = crate::auth::native::embedded_origin().is_some()`
   (`:1486`). `embedded_origin()` reads `TR_EMBEDDED_ORIGIN`
   (`app/src/auth/native.rs:24-26`), and the only thing in the repo that sets it is
   the Tauri shell at `src-tauri/src/lib.rs:194`. This page is *deliberately*
   terminal: the webview's 2-second `current_user` poll
   (`app/src/auth_pages.rs:183-194` + `app/src/account.rs:329-336`) claims the
   parked session. That is the desktop path the entry says works.
2. `app/src/lib.rs:1575-1594` — `/auth/app-return`, the **Android** deep-link
   bounce, *"You can close this tab once the app opens."* This one **does** try to
   return to the app: `:1589-1590` runs
   `location.replace("three-rings://auth/callback" + location.search)` plus a
   visible "Open the app" link (Chrome may require a gesture for custom schemes).
   It is a dead end only when opened where nothing claims the `three-rings://`
   scheme — i.e. in an ordinary browser with no app installed.

On the deployed web server `native` is `false`, so `/auth/callback` takes the
other branch: `app/src/lib.rs:1527-1550` — **303 to `/`** with `tr_session` +
`tr_jwt` set — and `/` dispatches authed users to `/my`
(`app/src/shell.rs:93-112`). Web never sees a "close this tab" page.

Reached only if the deployed app itself is misconfigured: setting
`TR_EMBEDDED_ORIGIN` in Render's environment would flip `:1486` to `native` and
make the deployed web callback serve page (1) — a terminal page with no poller
behind it, which is *exactly* the reported dead end. Nothing in the repo does
this (`Dockerfile:123-126` sets only `LEPTOS_*`; there is no `render.yaml`), and I
could not read Render's env vars — the Render MCP returned `unauthorized` for
workspace `tea-cspupujtq21c73boep00`.

### (c) "Works for desktop, not on web" → no code-level cause found
The rest of the web path checks out on inspection:
- `app/src/account.rs:398-409` — the `/auth/app-return` callback is chosen only
  when `native_origin.is_some() && cfg!(target_os = "android")`; a linux web
  server compiles that to `false`, so web gets `{origin}/auth/callback` and
  `{origin}/login?error=google`.
- `app/src/account.rs:416-421` re-hosts the upstream challenge as `tr_challenge`;
  `app/src/auth/cookies.rs:31-34` sets it `SameSite=Lax` — which *is* sent on the
  top-level cross-site GET redirect back from the auth service (`Strict` would
  have broken it).
- `app/src/auth/cookies.rs:57-78` derives origin/`Secure` from
  `x-forwarded-proto`/`x-forwarded-host`, with a unit test pinned to the Render
  host (`:100-111`).
- `app/src/auth/upstream.rs:306-329` sends `callbackURL`, `newUserCallbackURL`
  **and** `errorCallbackURL` — the first-time-Google production bug is already
  fixed here.
- `GoogleButton` is a **sibling** of the `<ActionForm>`, not inside it
  (`app/src/auth_pages.rs:293-318`), so there is no stray form-submit racing the
  `location.href` hand-off.

The plausible remaining causes are all environmental, not code: a missing/wrong
`NEON_AUTH_BASE_URL` on Render (`app/src/auth/upstream.rs:69-73` → the button
shows "Google sign-in isn't available right now"), the Render origin missing from
the upstream `trusted_origins`, or the `TR_EMBEDDED_ORIGIN` mis-set above. That
matches the triage's own open question ("If it's a config issue, it's S, not M").

## If it is real, what fixing it touches
- If it is the `TR_EMBEDDED_ORIGIN` misconfiguration: a Render env-var deletion.
  Zero code. Size **S**. Optionally harden `app/src/lib.rs:1486` so the
  native branch also requires the request to be non-proxied/loopback, so a stray
  env var cannot turn the public deployment into a single-user embedded server.
- If it is `NEON_AUTH_BASE_URL` / upstream `trusted_origins`: config only, plus
  possibly surfacing the upstream error text on the login card rather than the
  generic "isn't available right now" (`app/src/auth_pages.rs:201-203`).
- If a genuine code fault is found at runtime, the blast radius is
  `app/src/account.rs:377-428` (`google_sign_in`), `app/src/lib.rs:1476-1562`
  (`auth_callback`), `app/src/auth/cookies.rs`, and `app/src/auth_pages.rs:152-231`
  — shared by desktop and Android, so any change needs re-verification on all
  three surfaces (there is no automated coverage: `end2end/` has no Google test,
  and `auth-e2e.mjs` is email+password only).
- Bigger than it looks in one respect only: the flow cannot be exercised without a
  real Google consent, so every verification is manual.

## Open — needs a runtime check
Three, in cost order:

1. **Read Render's env vars for the web service** and confirm `TR_EMBEDDED_ORIGIN`
   is **not** set (and that `NEON_AUTH_BASE_URL` is). This alone would settle the
   "close this tab on web" observation — it is the only code path that can produce
   that page on the deployed app. (My Render MCP access was `unauthorized`.)
2. **Server-side probe, no browser:**
   `curl -sSi -X POST https://three-rings-6p5o.onrender.com/api/google_sign_in -H 'Content-Type: application/json' -d '{}'`
   → the returned `url`'s `redirect_uri`/`callbackURL` shows whether the deployed
   server hands the upstream `/auth/callback` (correct) or `/auth/app-return`
   (wrong), and the `Set-Cookie: tr_challenge=…; SameSite=Lax; Secure` proves the
   challenge is issued. An error body instead means env config. (Mints a
   throwaway 10-minute upstream challenge; creates no user.)
3. **The full manual repro** the triage asks for: on the deployed app, `/login` →
   "Continue with Google" with devtools network "preserve log" on, and record the
   URL chain. Expected: same tab → `accounts.google.com` → upstream `/callback/google`
   → `…/auth/callback?neon_auth_session_verifier=…` → 303 `/` → `/my`. Whichever
   hop is missing names the fault.
