### (a) `plan_move` → `None` closes the move dialog silently → **CONFIRMED**
Now `app/src/my/tree_manage.rs:1124-1128` (entry said `:951-955`):

```rust

    manage.move_open.set(false);

```

`plan_move` (`tree_manage.rs:1075-1102`) has **three** `None` exits and the caller
collapses them into one:

- `:1085-1087` — `req.forbidden.contains(&parent)` → destination became forbidden.
- `:1088` — `rows.iter().find(|r| r.summary.id == parent)?` → destination gone.
- `:1090-1092` — `new_parent == req.parent_id` → the genuine "already there".

The comment at `:1125` only names the third. The first two are exactly the stale-
snapshot cases the function's own doc comment at `:1082-1084` says it is guarding

### (b) A pick does nothing at all — no feedback, dialog left open → **CONFIRMED**

`busy` is confirmed shared across all four dialogs: one `RwSignal<bool>` on

So: real latent fragility, no demonstrated user-visible symptom. Graded PARTLY

### (f) `prevent_default()` only suppresses a keydown-sourced synthesized `contextmenu` → **CONFIRMED as a code shape; UNVERIFIABLE as a browser behavior**

Whether any shipped engine fires `contextmenu` from keyup rather than keydown is
not decidable from this repo.

## If it is real, what fixing it touches
- **(a) + (b)** are one fix, in one function: `commit_move`,
  `app/src/my/tree_manage.rs:1112-1168`, plus `plan_move`'s return type
  (`:1075-1102`) if the three `None` cases are to be distinguished — which they
  must be for (a). Bigger than it looks in two ways: `plan_move` is covered by six
  unit tests asserting `== None` (`:1374-1436`), all of which change shape; and
  the "destination gone / forbidden" arms want the same `error` + `toast`
  vocabulary `commit_drop` already established (`:1106-1111` documents that
  contract), so the fix should be read against `commit_drop` rather than invented.
  (b)'s `busy` half is arguably a `TreeManage` design question — a single shared
  latch across four dialogs — not a `commit_move` question.
- **(c) + (d)** are both in `app/src/components/ui/context_menu.rs` and both
  touch `restore_focus`. (c) needs the suppression to become per-item — a prop on
  `ContextMenuItem`, set only by `Move to…` in `tree_manage.rs:411-413`. That
  makes it a **registry-vendored component API change**, so `specs/ui-components.md`
  and the bench section `app/src/bench/context_menu.rs` come along; the bench check
  `end2end/bench-check.mjs:594-625` asserts ESC restores focus to the opener and
  would want a new case for the activate path. (d) is a two-line move of the reset
  out of the `else if`.
- **(e)** wants a case in `end2end/tests/collection-tree-move.spec.ts`'s keyboard
  describe (`:136`), pressing the chord on `[data-tree-row-head]`. Chromium-only
  per the e2e contract, which is also the engine least likely to expose (f).
- **(f)** cannot be fixed blind. If real, the fix is a guard flag set by the
  keydown handler and consumed by the `on:contextmenu` handler within one task —
  `tree.rs:479-505` plus the same shape in `context_menu.rs:169-187`.
- **(g)** is best fixed inside `DestinationList` itself
  (`app/src/catalog/destination.rs:258-292`) rather than at two call sites — but
  `CommandEmpty` derives emptiness from the `Command` registry it has no loading

  `tree_manage.rs:800`, `move_selection.rs:672`.
- **(h)** — see the shared-panel note above. Fixing it means threading
  `menu_target` identity or `ContextMenuContext.target_id` out to the triggers, so

  Pairs with P6-017e by construction.

- **(j)** is a no-op unless the tree gets deep; nothing to touch.
