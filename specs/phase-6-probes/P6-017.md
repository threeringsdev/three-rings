## Verdict: CONFIRMED

All eight sub-claims are still true. Every cited line still blames to `363691ff`
(`feat(ui): collection-header kebab…`, #75) — the commit the review round was
reviewing. Nothing in the bundle has been fixed. Only the **line numbers** have
drifted (by +32 to +80), because #76 and #77 edited other parts of the same files.

One clause is **literally wrong but substantively right**: (a) says the confirm
"says `0 nested collections`". It does not — the copy is guarded by
`if descendants > 0`, so in the degraded state the phrase is **silently omitted**
rather than printed as zero. The defect it names (a destructive confirm that does
not mention the collections it is about to cascade away) is real either way; the
wording of the entry should be corrected when the task is worked.

## Evidence

### (a) `find_node` miss degrades `forbidden` to `{self}` → delete confirm undercounts — **CONFIRMED (wording off)**
- `app/src/my/tree_manage.rs:86-93` — cited as `86-93`, **unmoved**. `for_collection`
  still does `match find_node(roots, c.id) { Some(node) => subtree_ids(…), None => { forbidden.insert(c.id); } }`.
- The miss is reachable: `app/src/my/collection.rs:660` calls
  `assembled_roots(tree.get_untracked().flatten())`, and `assembled_roots`
  (`collection.rs:378-385`) returns `Vec::new()` for **any** non-`Some(Ok(_))` tree —
  a failed read, an anonymous shell, or a read still in flight. So the degrade is
  a plain `Vec::new()` → `find_node` → `None`, not an exotic path.
- `open_delete` (`tree_manage.rs:320-344`) moves `forbidden` straight into
  `DeleteReq::subtree`, and `DeleteReq::descendants()` (`:134-136`) is
  `subtree.len().saturating_sub(1)` = **0**.
- The confirm copy is `tree_manage.rs:737-758`. The `descendants > 0` guard at
  `:742` means the string becomes
  `"This permanently deletes {cards} cards inside it. This cannot be undone."` —
  **no mention of nested collections at all**. The entry's "says 0 nested
  collections" is inaccurate; the omission is the actual behavior.
- The card number stays honest in the degraded state: `cards` comes from
  `totals.present_total()` (`collection.rs:658`), and
  `shared/src/collection.rs:331-333` defines that as `present + present_rollup`
  — already rolled up over the subtree. So the confirm names the right card count
  while silently dropping the folder count. That asymmetry makes the lie harder to
  spot, not easier.
- The server does cascade: `app/src/backend/hosted.rs:508-521` is a bare
  `DELETE FROM collections WHERE id = $1 AND NOT is_inbox`, and
  `migrations/0003_collections.sql:23` is
  `parent_id uuid REFERENCES collections(id) ON DELETE CASCADE`. Children go.

Second-order consequence the entry does not mention: the same degraded
`subtree` is what `route_after_delete` (`tree_manage.rs:152-165`) tests the
route against. On the header-kebab path the route *is* the deleted node, so the
navigation still fires; but a delete issued from a **tree row** while standing on
one of its descendants would leave the page on a dead id. Not in scope for this
entry, and the tree-row path builds `forbidden` from a real `find_node` hit, so
it is latent rather than live.

  source tuple is `move || (url_q.get(), url_cursor.get(), revision.get())`, where

- `grep -n "TreeManage" app/src/my/all_cards.rs` → **no hits**. The file never
  touches `TreeManage::revision`.
- The stale value is user-visible: `all_cards.rs:485` renders
  `format!("{} in {}", loc.quantity, loc.collection_name)` and `:524` the
  multi-location variant — `collection_name` is baked into the payload.
- Nothing else rescues it. A sidebar rename does `tree.refetch()` + a

  `route_after_delete("/my", …)`, which returns `None` at `tree_manage.rs:155`
  (the path does not start with `/my/collections/`), so there is no navigation to

### (c) `manage.revision` as a `view_res` source re-seeds every stepper — **CONFIRMED**
- Cited `collection.rs:150`; now `app/src/my/collection.rs:173-182`.
  `manage.revision.get()` is the fifth source at `:180`.
- The rebuild is real: the body `<Transition>` at `:330-370` re-runs its `Suspend`
  on every new `view_res` value and re-emits `<CollectionTable view folders here_delta tree />`
  at `:355`, constructing fresh `CountStepper`s.
- The repo attests the mechanism itself. The module doc at `collection.rs:27-28`:
  "A commit does **not** refetch the view: remounting the row would dispose the
  stepper the undo toast is about to call back into." The defect narrative the
  entry cites at `236-243` now lives at **`collection.rs:269-278`**, unchanged in
  substance.
- The failure mode is slightly different from the one documented, and still ends
  in "Undo silently did nothing". `app/src/components/ui/count_stepper.rs:214-227`:
  ```rust
  let undo = Callback::new(move |()| {
      let Some(cur) = value.try_get_untracked() else {
          return;
      };
      if cur != from { … }
  });
  ```
  The originally-documented path was `cur == from` (row re-seeded from a *stale*
  fetched count). With `manage.revision` in the source tuple the refetch returns
  the **committed** count, so the old `value` signal is simply **disposed** and
  `try_get_untracked()` returns `None` — the early `return` at `:218`. Different
  branch, identical user-visible outcome: the toast's Undo does nothing and
  reports nothing.
- Precondition worth recording: the toast auto-dismisses at
  `duration_ms: 5000` (`app/src/components/ui/sonner.rs:71`), so the tree mutation
  has to land inside a ~5 s window. A sidebar `New binder inside…` or `Delete…`
  fits; a rename you have to type into is tighter. Narrow, but the removal path
  (`collection.rs:1482-1511`) is *not* exposed — it uses `try_update`/`try_set`
  throughout and re-drives the server, so only the plain count-commit undo fails.

### (d) In-flight `view_res` refetch aims the kebab at the previous payload — **CONFIRMED**
- Cited `collection.rs:588`; now `app/src/my/collection.rs:659-666`. `aim` closes
  over `collection = StoredValue::new(view.collection.clone())` (`:651`) — a
  snapshot of the payload that rendered *this* `CollectionHeader`.
- `<Transition>` at `:279-301` is the whole point: it keeps the previous
  `CollectionHeader` mounted and interactive while a new `view_res` is in flight.
  A `url_id` change (a sidebar click to another collection) is a source change at
  `:176`, so the window is exactly "navigated, payload not back yet".
- The consequence is worse than "names the wrong collection". `submit_delete`
  (`tree_manage.rs:553-595`) deletes `req.id` — the *old* collection — and then
  `route_after_delete(&pathname.get_untracked(), &req)` compares the **new** URL
  against the **old** subtree, gets `None` at `:158`, and takes the no-navigation
  branch at `:586`. So the user deletes a collection they are no longer looking
  at, and the app does not move. Silent wrong-target destruction.
- The same-URL refetch case (a `manage.revision` bump) is harmless: the "previous
  payload" is the same collection. Only a URL change opens the bad window.

### (f) `leaving` computed before the await — **CONFIRMED**
- Cited `tree_manage.rs:533`; now `app/src/my/tree_manage.rs:565`:
  `let leaving = route_after_delete(&pathname.get_untracked(), &req);`, preceded by
  the comment "Decided *before* the await, off the route the confirm was answered on."
- `spawn_local` opens at `:567`, the `await` is at `:568`, and the success arm at
  `:573-578` fires `navigate(&to, …)` unconditionally on `Some(to)`. A navigation

  that choice, not an oversight. Fixing (d) and (f) together means deciding, once,
  whether the delete flow trusts the confirm-time route or the response-time route.

## If it is real, what fixing it touches

**(a)** — `tree_manage.rs:86-93` plus the confirm copy at `:737-758`. Cheaper than
it looks: `CollectionHeader` already holds `view.children` (immediate child
summaries, straight off the page's own payload, no tree read), so the degraded
case can at minimum say "and the collections inside it" instead of nothing. An
*exact* count in the degraded state would need the server to return a subtree
count — an API change to `CollectionView`/`collection_view`, which is what makes
the full fix bigger than the one-liner. A third option is to withhold `Delete…`
entirely when `find_node` misses, which is honest but degrades the kebab exactly
when the tree read is flaky.

**(b)** — `all_cards.rs:163-167`: add `expect_context::<TreeManage>().revision` as a
fourth source. Watch the cost: `/my`'s aggregate read is expensive, and this makes
*every* tree mutation refetch it. `all_cards.rs:84-114` also documents a live
resource-slot cross-decode hazard on this exact resource — changing its source
tuple should be checked against that doc, not just compiled.

**(c) and (d) and (f)** are one design decision, not three fixes. All three come
from the same call: the delete/kebab flow snapshots at open-time and the page
rebuilds on `view_res`. Options interact — e.g. making the kebab re-read the URL at
click time (fixes d) also changes what `route_after_delete` should compare against
(f), and narrowing `view_res`'s sources so a tree mutation refreshes only the
header/folder rows rather than the card table (fixes c) is a restructure of the two
`Transition` blocks at `collection.rs:279-370`. Doing them one at a time will
produce three partial fixes that argue with each other.

**(e)** — `collection.rs:873` and `tree.rs:567`, both driven off
`use_context_menu()`'s open state. The triage note "fix both together" is right:
the two triggers share one `menu_target` and one `TreeMenu`, so a one-sided fix is
a new inconsistency. Pattern to copy: `collapsible.rs:71`. Small and self-contained.

**(g)** — `bench/header_kebab.rs`. Either provide stub `TreeManage` +
`CollectionTreeResource` contexts on the bench page so the real `TreeMenu` mounts,
or leave the stand-in and make the *page* say so. Note `CLAUDE.md` requires a bench
section to ship with its component, so whatever is chosen sets precedent for the
next app composite that cannot mount its real dependencies.

**(h)** — one line, `collection-header-kebab.spec.ts:429-431` → the
`h1:visible` + `toHaveCount(1)` pair. Trivially separable from everything else in
this bundle.

## Open — needs a runtime check

Three claims are confirmed by construction but not observed running. None of them
change the verdict; they would settle *severity*.

1. **(c) — does the toast actually outlive the rebuild?** The check: with
   `cargo leptos watch` up, open a collection with a stepper-backed card, commit a
   count change (toast appears), then within 5 s create a collection from the
   sidebar (`New binder inside…` is the fastest tree mutation), then click **Undo**
   on the still-visible toast. Expected if the claim holds: the number does not
   revert and no error toast appears. Confirming that the `Toaster` is mounted
   above the `Transition` (so the toast survives the table rebuild) is the specific
   thing I could not settle by reading — if it is inside the rebuilt subtree, the
   toast vanishes with the table and (c) is a non-issue.

2. **(d) — how wide is the window in practice?** The check: throttle the network
   (DevTools "Slow 3G"), click a sidebar collection to navigate, and while the old
   header is still on screen click its `⋯` → `Delete…`. Expected if the claim
   holds: the dialog title names the collection you *left*, and confirming deletes
   it while the URL stays on the new one with no navigation. On a fast local
   connection the window may be too short to hit by hand — throttling is what makes
   this observable, and its width on a real connection is the severity question.

3. **(a) — is the degraded path reachable without devtools?** Reading says yes
   (any failed/in-flight tree read), but I could not produce one. The check: block
   the `list_collections` server-fn response in DevTools, load
   `/my/collections/{id}` for a collection that has children, open the header `⋯` →
