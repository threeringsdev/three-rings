# P6-059 — `scripts/migrate.sh` can print `migrations: up to date` on a run that embedded no new migration
Probed 2026-07-28 against 91634da.

## Verdict: CONFIRMED

Every structural clause of the entry is still true at HEAD: the embed is still
non-deterministic, the only defense is still the `touch`, and the success line is
still printed on any `Ok(())` with no reference to what (if anything) was applied.
`scripts/migrate.sh` has not been touched since the `touch` workaround landed on
2026-07-15.

## Evidence

- **"its `touch app/src/db.rs`" is still the whole mechanism** → CONFIRMED —
  `scripts/migrate.sh:73-80`. The script ends with `touch "$root/app/src/db.rs"`
  followed by `MIGRATION_DATABASE_URL="$url" cargo run --quiet -p server -- --migrate`.
  The comment above it names the exact failure mode the entry describes
  ("`--migrate` reports 'up to date' without applying it (observed 2026-07-15 on
  the devcontainer overlay fs)"). `git blame` puts lines 73-78 at `f019b2b`
  (2026-07-15); `git log --oneline -- scripts/migrate.sh` shows only two commits
  ever, the latest being that one. Nothing has been added since.

- **The embed is genuinely non-deterministic (not merely "was once flaky")** →
  CONFIRMED, root cause identified. `app/src/db.rs:19` is
  `static MIGRATOR: sqlx::migrate::Migrator = sqlx::migrate!("../migrations");`.
  In sqlx 0.8.6 (`Cargo.lock:5549`, `sqlx-macros`), the macro expansion emits one
  `include_str!(<abs path>)` per migration file that existed **at expansion time**
  (`sqlx-macros-core-0.8.6/src/migrate.rs:63`). Directory-level tracking exists in
  that same file at line 110-120 — `proc_macro::tracked_path::path(path)` — but it
  is behind `#[cfg(any(sqlx_macros_unstable, procmacro2_semver_exempt))]`, and
  neither cfg is set in this repo (`.cargo/config.toml` sets only
  `LEPTOS_OUTPUT_NAME`; no `RUSTFLAGS` in any Cargo/CI/Dockerfile/script). So cargo
  has **no dependency edge on the `migrations/` directory** — adding `0009_move_boards.sql`
  cannot by itself invalidate the `app` fingerprint. The canonical fix (a
  `build.rs` emitting `cargo:rerun-if-changed=migrations`) is absent: the only
  `build.rs` in the workspace is `src-tauri/build.rs`.

- **The success message is unconditional on work done** → CONFIRMED —
  `server/src/main.rs:21-31`. `app::db::migrate()` returns `Ok(())` and main logs
  the literal `"migrations: up to date"`. `app/src/db.rs:41-56` calls
  `MIGRATOR.run(&pool)`, which returns `Ok` whether it applied nine migrations or
  zero, and neither layer reports which versions are embedded or which were
  applied. The output of "applied 0009" and "ran a stale binary that has never
  heard of 0009" is byte-identical. Compounding it, the build is run with
  `cargo run --quiet` (`scripts/migrate.sh:80`), which suppresses the compile
  lines — so the operator has no visible signal that `app` was even recompiled.

- **"or have the script verify against the database rather than the binary"
  (i.e. no such verification exists today)** → CONFIRMED — a repo-wide grep for
  `_sqlx_migrations`, `sqlx migrate`, and `migrate info` across `*.sh`, `*.rs`,
  `*.yml`, `*.md`, `Dockerfile*` returns **zero** hits outside `target/`. Nothing
  anywhere compares `migrations/*.sql` on disk to the applied set in the database.

- **The specific incident ("did not force the re-embed in time, and a second run
  applied it")** → UNVERIFIABLE from the repo, but immaterial to the verdict. That
  observation is not recorded in any spec. `specs/data-model.md:555-559` records
  the *earlier* (2026-07-15, pre-`touch`) occurrence that the `touch` was added to
  fix, and still asserts the `touch` "guarantee[s] a re-embed" — a claim the
  mechanism above does not support, since it rests entirely on mtime comparison
  and cargo treats a source as changed only when its mtime is strictly newer than
  the artifact's. On a coarse- or cached-mtime mount (the devcontainer's
  virtiofs/overlay stack) a `touch` landing inside the same second as the previous
  build's output is not guaranteed to register. The entry's claim that this is a
  *possible* failure, not a fixed one, is what the code supports, and it does.

- **Stakes clause ("the one manual step that gates a prod deploy")** → CONFIRMED
  and, if anything, understated at HEAD. `specs/data-model.md:475-488` establishes
  Option B: `scripts/migrate.sh prod` from the dev container is the only path that
  applies DDL to prod; CI never touches Neon and Render has no pre-deploy hook on
  the free tier. `specs/app-ui.md:1391-1402` states migration `0009` is **not**
  expand-first in the new-code direction: on an unmigrated prod every write path
  fails `42703 column "to_board" does not exist` → 502 while reads stay green, so
  "the app looks alive while every write errors behind a toast", and "nothing
  enforces the ordering". A false `up to date` is exactly the input that produces
  that state.

- **Gating** → both cited specs are `implemented`
  (`specs/delivery-pipeline.md:3`, `specs/data-model.md:3`), so the task is not
  blocked on spec review.

## What changed since the entry was written

Nothing in the affected code. `scripts/migrate.sh`, `app/src/db.rs`'s `MIGRATOR`,
and `server/src/main.rs`'s `--migrate` arm are all unchanged since `f019b2b`
(2026-07-15). Migrations `0007`, `0008`, `0009` were added in the interval, which
raises exposure (each new `.sql` file is another chance for the stale-embed race)
but changes nothing about the mechanism. `specs/data-model.md:555-559` still
describes the `touch` as a guarantee; that sentence is now known to be wrong and
would want correcting as part of any fix.

## If it is real, what fixing it touches

Small and self-contained — size S holds. Two independent fixes, and the entry's
own wording ("or") suggests either; both are cheap and they are complementary:

1. **Deterministic embed.** Add `app/build.rs` with
   `println!("cargo:rerun-if-changed=../migrations");` (path relative to the `app`
   crate, since `sqlx::migrate!("../migrations")` resolves against
   `CARGO_MANIFEST_DIR`). Then delete the `touch` from `scripts/migrate.sh:73-78`.
   Watch-out: `app` currently has no build script, so this adds one to a crate
   compiled for three targets (`hosted`, `native`, `hydrate`/wasm) — it must be
   unconditional and side-effect-free, and it slightly perturbs the CI rust-cache
   fingerprints on first run.
2. **Verify against the database, not the binary.** `MIGRATOR.run()` discards what
   it applied, so the honest report needs the applied set read back: sqlx's
   `Migrate::list_applied_migrations` (on a `PgConnection`) compared against
   `MIGRATOR.iter()`, logged as concrete version numbers. That touches
   `app/src/db.rs:41-56` (return the applied/embedded versions instead of `()`)
   and `server/src/main.rs:21-31` (print them instead of the fixed string). This
   is the change that actually removes the "success having done nothing" failure
   mode — (1) alone makes the race unlikely, but a silent-success report stays
   silent about any *other* cause of a no-op run (wrong branch URL, stale binary
   from a cross-target build, an aborted `cargo run`).

Also worth folding in: drop `--quiet` from `scripts/migrate.sh:80` (or keep it and
rely on the version log), and correct the now-false "guarantee[s] a re-embed"
sentence at `specs/data-model.md:555-559`. `scripts/ingest.sh:58` uses the same
`cargo run --quiet -p server -- --ingest` shape but has no embed dependency, so it
is out of scope.

## Open — needs a runtime check

Not needed to settle the verdict — the missing `rerun-if-changed` edge is
sufficient on its own — but if reproduction of the exact mtime race is wanted:
in the devcontainer, with `app` freshly built, add an empty
`migrations/0010_probe.sql`, immediately run `touch app/src/db.rs && cargo build -p server`
and check whether `app` is listed as recompiled (`cargo build -v` / `--timings`);
repeat with the `touch` removed to confirm a new `.sql` file alone never triggers
a rebuild. The second half of that check is the load-bearing one and is
deterministic — it will show no rebuild every time.
