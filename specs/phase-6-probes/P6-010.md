# P6-010 — An idle tab tells signed-in users their session expired: `fetch_current_user` falls back to `tr_session`, `user_id_from_headers` does not
Probed 2026-07-28 against 91634da.

## Verdict: CONFIRMED

Every structural claim holds, both cited `file:line` spans still say exactly what
the entry says they say, and nothing has touched either function since the entry
was written. One clause is imprecise (the error string), and one clause is
narrower than written (it is a **hosted-backend-only** defect — the native
backend already implements the fix). Neither changes the verdict.

- **"the refreshed JWT lands on the *response*, so data reads inside that same SSR
  pass still see the stale request header"** → CONFIRMED, and the sequencing makes

  (`app/src/account.rs:78-100`) only calls `append_set_cookie`, which pushes onto
  `leptos_axum::ResponseOptions` (`account.rs:66-73`); it never mutates the request
  `HeaderMap`. Every data read re-extracts the *request* headers fresh
  (`leptos_axum::extract::<HeaderMap>()`, `lib.rs:836`). And
  `provide_collection_tree` (`app/src/my/tree.rs:40-51`) explicitly `user.await`s

  the guard provably resolves before the read that then 401s.

- **"self-healing on one extra click (the response did refresh the JWT)"** →
  CONFIRMED, with the mechanism intact. All `/my/*` routes are `ssr=SsrMode::Async`
  (`app/src/lib.rs:127-154`), so the whole page renders before the head is flushed
  and the accumulated `Set-Cookie` headers do reach the client. The next request
  therefore carries a fresh `tr_jwt`.

- **"15-minute window"** → CONFIRMED. `JWT_MAX_AGE = 15 * 60` vs
  `SESSION_MAX_AGE = 7 * 24 * 60 * 60` (`app/src/auth/cookies.rs:24-26`), documented
  as mirroring the measured upstream lifetimes.

- **"Same request, same expired cookie → `unauthorized: invalid token`"** →
  IMPRECISE, outcome unaffected. The `tr_jwt` cookie is set with
  `Max-Age=900` (`cookies.rs:31-34`), the same 15 minutes as the token itself, so
  the *browser* usually drops the cookie at expiry and the request arrives with no
  `tr_jwt` at all. That takes the `.ok_or(AuthError::MissingToken)` arm →
  `"unauthorized: missing bearer token"`, not `"invalid token"`. Both strings
  classify to `Failure::Session` and both render `data-failure="session"`, so the
  user-visible defect is identical; only the wire string in the entry is wrong.
  (The repo's own pinning test at `app/src/my/tree.rs:735` asserts on the
  `"unauthorized: invalid token"` spelling too, so the imprecision is consistent
  across the repo, not introduced by the entry.)

- **Scope: "every `/my/*` surface"** → TRUE but under-specified — it is
  hosted-only. The native/Tauri build already has the fix the entry proposes:
  `collection_backend()`'s native arm (`lib.rs:844-861`) hands `NativeBackend` both
  `tr_jwt` **and** `tr_session`, and `NativeBackend::send`
  (`app/src/backend/native.rs:115-145`) does a silent `mint_jwt` re-mint from the
  session plus one retry on any 401. So the two backends disagree about the same
  rule, and the desktop/mobile shell is unaffected.

## If it is real, what fixing it touches

Candidate A — give the hosted path a session fallback:
- `app/src/backend/routes.rs:119-124` (`session_backend`) and `:106-111`
  (`catalog_backend`), or `app/src/auth.rs:233-239` itself.
- Doing it in `user_id_from_headers` also changes the `AuthUser` extractor
  (`auth.rs:222-225`) and therefore the hosted JSON API that the native client
  calls — where a `tr_session` fallback is meaningless (that client sends a Bearer
  header) and would add an upstream `mint_jwt` round trip to the 401 path of the
  *terminus*. Doing it in `session_backend`/`catalog_backend` confines it to the
  web UI's server fns, which is where the defect is.
- Either way this adds a **real network round trip** to the data path, on both
  backends. The hosted app is the *data*-authorization terminus (it owns the pool
  and the RLS transaction) but it is **not** the token issuer: it only ever
  verifies, against a fetched JWKS (`auth.rs:96-181`, `DecodingKey`/`decode`), and
  there is no `EncodingKey` or `jsonwebtoken::encode` anywhere in `app/` or
  `shared/`. `auth::upstream::mint_jwt` (`app/src/auth/upstream.rs:262-281`) is a
  `reqwest` `GET <NEON_AUTH_BASE_URL>/token` via `call` (`upstream.rs:88-132`),
  with zero `cfg(feature = …)` gates in the whole module — so the hosted arm is the
  same HTTP call, not a local sign and not a DB lookup. It therefore needs the same
  "exactly once, then surface the 401" discipline `native.rs:132-144` already has.
- **Cheapest hosted shape: resolve, don't persist.** The fallback only has to
  produce a `user_id` for this request; it does not need to write a refreshed
  `tr_jwt`, because `fetch_current_user` already refreshes the cookie on the same
  response. That matters concretely: `session_backend`/`catalog_backend` are shared
  with the plain-axum handlers in `routes.rs`, which have no Leptos context, so
  calling `append_set_cookie` (`account.rs:66-73`, `expect_context::<ResponseOptions>()`)
  from there would panic on the native-client route path.

Candidate B — make the refreshed JWT visible to the pass that refreshed it:
- Needs somewhere per-request to stash the freshly minted JWT that
  `lib.rs:836`'s `extract::<HeaderMap>()` cannot see. Touches
  `account.rs:78-100` (`establish_session`), `lib.rs:834-842`, and both
  `routes.rs` helpers — i.e. a request-scoped context the whole SSR pass reads
  instead of the raw request headers.

Bigger than it looks because:
- `app/src/my/tree.rs:726-739` pins the current behavior in a unit test whose
  comment *documents this bug as the reason* `Failure::Session` is non-retryable.
  A fix makes that test's rationale stale (the assertion itself stays correct).
- `specs/app-ui.md:439-462` records the mechanism at length and would need
  updating; `specs/auth.md` carries nothing on it and probably should.
- The e2e suite asserts the `session` arm at `end2end/tests/states.spec.ts:460`
  (bench-driven, so not itself a regression risk).
- The right framing is "make hosted obey the rule native already obeys" — but note
  that `native.rs:126-145` is a reusable **pattern, not reusable code**. Its
  re-mint hangs off a `reqwest::Response` with status 401 and a `self.refresh`
  field; the hosted path has no HTTP response to inspect and fails earlier, at
  `user_id_from_headers` returning `AuthError`. The actual reusable *code* for the
  hosted fix is `fetch_current_user`'s own fallback (`account.rs:325-338`) —
  read `tr_session`, `mint_jwt`, `verify_token` — minus the cookie writes.

## Resolution (2026-08-12)

Shape built: **Candidate A**, confined to `collection_backend()`'s hosted arm
(`app/src/lib.rs`) — not `auth.rs`'s `user_id_from_headers`/`AuthUser` extractor, and not
`backend/routes.rs`'s `catalog_backend`. Both of those are shared with the plain-axum routes
the native client's `NativeBackend` calls over HTTP (`backend/native.rs`), which already
re-mints for itself on a `401` (`native.rs:132-144`); adding a second fallback underneath it
would mean the hosted terminus silently re-mints on *its own* 401 response to the native
client's already-re-minted retry, doubling the round trip for no benefit and contradicting the
"the native client owns its own retry" split the codebase already draws.

**The helper.** `user_id_with_session_fallback(headers: &HeaderMap) -> Result<Uuid, AuthError>`,
private in `app/src/lib.rs`, called from `collection_backend()`'s hosted arm and from a new
`catalog_backend_with_fallback` (see below). It calls `user_id_from_headers` once; on success it
returns the id directly. On `AuthError::MissingToken` or `AuthError::InvalidToken` **and** a
present `tr_session` cookie, it reads the session, calls `auth::upstream::mint_jwt`, then
`verify_token` on the result, and resolves `Uuid::parse_str(&claims.sub)` — the same three steps
`fetch_current_user` already performs (`account.rs:320-344`), minus the `append_set_cookie`
calls: the data path only has to name a user for *this* request. On a **document** request,
`fetch_current_user` (awaited by `RequireAuth` earlier in the same SSR pass) refreshes
`tr_jwt` on the response and the window closes. Post-hydration server-fn calls have no such
refresh (`CurrentUserResource` never refetches), so a tab idle past the cookie life pays one
mint round trip per server fn until its next full document load — the per-call pattern
`NativeBackend::send` already established. Persisting the fresh JWT from the helper via
`use_context::<ResponseOptions>()` would make it genuinely once per idle window; filed as a
follow-up task alongside the native catalog gap.

`Configuration`/`Jwks` errors are **not** retried — deliberately narrower than "any failure of
the primary lookup." Both are server misconfiguration (a bad/unset `NEON_AUTH_BASE_URL`, a
broken JWKS fetch), not a stale token; the fallback's own `verify_token` call would hit the
exact same broken verifier and fail identically, so attempting it would only spend a wasted
upstream round trip. The probe's imprecision note (missing vs. invalid token) resolved in favor
of covering **both**: the cookie's `Max-Age=900` matching the JWT's own 15-minute expiry means
the browser usually drops it outright (`MissingToken`), but nothing guarantees that in every
client, so `InvalidToken` is equally in scope.

**Exactly-once is structural, not a comment.** The decision of *whether* to attempt a mint is
split into a separate, synchronous, I/O-free function, `decide_fallback(primary: Result<Uuid,
AuthError>, session_cookie: Option<String>) -> FallbackDecision`, returning either `Settled(_)`
(use the primary result or its error as-is, no mint) or `TryMint { session, original }`. The
async shell (`user_id_with_session_fallback`) matches on that decision once; `upstream::mint_jwt`
appears at exactly one call site, inside a straight-line body with no loop and no recursion back
into the function. Any failure along the fallback path (`let…else`) returns `Err(original)`
immediately — the *primary* lookup's error, not a new one — so a mint failure cannot cascade into
a retry loop; it just surfaces the same 401 the caller would have gotten without the fallback.

**Catalog extension: included.** `catalog_backend_with_fallback` in `app/src/lib.rs` is the same
`user_id_with_session_fallback` call, wrapped in the catalog's existing opportunistic
match-and-degrade shape (`Ok(id) => HostedBackend::for_user(id)`, `Err(_) =>
HostedBackend::anonymous()`) instead of the collection path's hard 401. It replaced
`backend::routes::catalog_backend` at both of its two call sites in `lib.rs`
(`search_catalog`, `card_detail`) — `backend::routes::catalog_backend` itself is untouched and
still serves `routes.rs`'s own plain-axum handlers (the native client's HTTP path). This
qualified as "literally the same helper call dropped in": no new cookie parsing, no new upstream
call shape, just composing the already-built helper into the already-existing opportunistic
pattern. Net effect: `/catalog` and `/cards/:id` ownership blocks (which decide whether
`CardDetail::ownership`/owned-counts are `Some`) now survive the idle-tab window too, instead of
silently degrading to the anonymous view — the same class of bug as the collection 401, just
manifesting as missing data instead of an error state.

**A necessary side-effect: `backend::routes::session_backend` was deleted.** It existed solely
as `collection_backend()`'s old hosted-arm auth step; nothing else called it (unlike
`catalog_backend`, which `routes.rs`'s own catalog handlers also use directly for the native
path). Once `collection_backend()` switched to `user_id_with_session_fallback` it became dead
code and the `-D warnings` gate would have failed on it.

**Unit tests** (`app/src/lib.rs`, `session_fallback_tests`, 7 cases): all pin `decide_fallback`'s
pure decision shape — primary success settles without a mint even with a session cookie present
(covers "jwt present+valid → no mint attempted", since a *real* valid JWT can't be constructed
in a unit test without Better Auth's signing key); `MissingToken`+no session settles on the
original error (missing both cookies → original error surfaced); `MissingToken`/`InvalidToken`
+session both route to `TryMint`; `Configuration`/`Jwks`+session both stay `Settled` (not
retried). One `#[tokio::test]` exercises the real async shell end-to-end with no cookies at all,
confirming it resolves immediately with no network I/O. **Untestable at unit level**: the
mint+verify round trip itself (`upstream::mint_jwt` against a real Better Auth instance,
`verify_token` against a real signed JWT) — no Better Auth mock exists in this repo, and building
one was out of scope. That path is covered by the e2e test below instead.

**e2e** (`end2end/tests/session-fallback.spec.ts`, tag `@fast`): logs in via the fixture, deletes
`tr_jwt` from the browser context (keeps `tr_session`), does a full `page.goto('/my/all')`, and
asserts no `[data-failure="session"]`, the fixture user's real collection content renders, and a
fresh `tr_jwt` cookie exists after the navigation. Kill-verified against `main` (stashed
`app/src` changes): the test failed exactly as predicted — `data-failure="session"` present,
zero collection rows — then passed once the changes were restored. See the task's final report
for the literal command output.

**Open follow-up, not filed as a separate task**: the native backend's own re-mint
(`native.rs:132-144`) and this hosted fallback are two independent implementations of the same
"stale JWT + live session → re-mint" rule, per the probe's own note that `native.rs`'s shape is
"a pattern, not reusable code" against a `reqwest::Response`. They still agree in outcome but
not in code; unifying them would need a shared abstraction over "how do I get a fresh JWT from
here" that abstracts away *where* the 401 information comes from (a `reqwest::Response` status
vs. an `AuthError` from a local verify), which is bigger than this fix and not obviously worth
it for two call sites.
